# LLM 平台 · 面试技术文档

> 一份完整的面试讲稿：架构、技术选型、MVC 分层、遇到的难题与解决思路。
> 项目规模：后端 ~57K 行 Python（20 个模块），前端 ~8K 行 TypeScript，24 个测试文件（207 个测试全绿）。

---

## 一、项目定位（一句话）

一个**分层清晰、可落地、可演进**的生产级 LLM 应用平台。核心叙事是——**用工程确定性驾驭模型不确定性**。

它不是"调 LLM API 的 demo"，而是把 LLM 应用开发中**真正难的部分**——Agent 编排、记忆、RAG、安全、韧性、成本、灰度——系统性地落地。

---

## 二、总体架构（十层 + 三大体系）

### 2.1 十层水平分层（依赖方向）

```
api → services → domain → [repositories / infrastructure]
                        ↘ agents → mcp → [memory / rag]
                          security / observability / resilience / evaluation 横向
                          core 最底层，被所有层依赖，不依赖任何层
```

| 层 | 目录 | 职责 |
|---|---|---|
| **core** | `src/core/` | 异常体系 + 工具契约 + 共享类型（最底层，不依赖任何层） |
| **api** | `src/api/` | FastAPI 路由 + 依赖注入 |
| **agents** | `src/agents/` | Agent 模式（ReAct/PEV）+ 7 种编排 + 业务专家 |
| **mcp** | `src/mcp/` | MCP Server/Client + 内置工具（CLI/文档/OCR）+ 授权 |
| **memory** | `src/memory/` | 五层记忆（STM/LTM/Episodic/遗忘曲线） |
| **rag** | `src/rag/` | 全链路 RAG（chunk/embed/检索/生成） |
| **repositories** | `src/repositories/` | ORM 持久化（禁止 ORM 穿透） |
| **infrastructure** | `src/infrastructure/` | config/redis/broker/LLM 适配器 |
| **security** | `src/security/` | auth/RBAC/ABAC/PII |
| **observability** | `src/observability/` | metrics/tracing/health/audit |
| **resilience** | `src/resilience/` | 分层超时/重试预算/断点恢复/资源 TTL |
| **domain** | `src/domain/` | 对话/上下文/token/prompt 领域模型 |

**为什么分层能防循环依赖**：依赖方向严格单向，任何一层不能反向 import。这从结构上杜绝了 God Class 和循环依赖。18/18 模块 import 无循环依赖（测试验证过）。

### 2.2 三大生产级思考体系（横向能力）

| 体系 | 目录 | 核心思想 |
|---|---|---|
| **Harness** | `src/harness/` | 用工程确定性驾驭模型不确定性（Agent 护栏） |
| **Herms** | `src/herms/` | 评估驱动的自进化闭环（H-E-R-M-S） |
| **RAGAS** | `src/ragas/` | 用标准化指标量化 RAG 质量 |

## 三、MVC 架构（代码可读性）

我严格遵循 MVC 分层，让代码一眼能看懂、能讲清：

| MVC | 后端 | 前端 |
|---|---|---|
| **Model**（数据） | `domain/` + `repositories/`（领域模型 + ORM 持久化） | `store/`（Zustand 状态，真实 API，无 mock） |
| **View**（展示） | `api/schemas/`（Pydantic DTO） | `components/` + `pages/`（React 组件） |
| **Controller**（控制） | `api/routes/` + `services/`（路由 + 业务编排） | `api/`（axios 层）+ `hooks/`（自定义 hooks） |

**具体对应关系**：

```
前端请求 → api/routes/（Controller）→ services/（业务编排）
                                      ↓
                              domain/（Model 业务逻辑）
                                      ↓
                              repositories/（Model 持久化）
                                      ↓
                              PostgreSQL / Redis / Milvus
```

前端侧：
```
用户点击 → pages/（View 组件）→ store/（Model 状态，Zustand）
                                    ↓
                            api/（Controller，axios 请求）
                                    ↓
                            后端 REST API
```

**好处**：每个请求从 View → Controller → Model 的单向数据流，职责清晰，容易单元测试（Model 层纯逻辑、Controller 层 mock API、View 层快照测试）。

## 四、技术选型（及选型理由）

| 领域 | 选型 | 理由 |
|---|---|---|
| **后端框架** | FastAPI（async） | 原生 async，自动 OpenAPI 文档，Pydantic 校验 |
| **LLM 编排** | LangGraph StateGraph | 状态机 + 断点续跑 + 人机协作，比裸 LangChain 更适合复杂 Agent |
| **LLM 接入** | 自研 AI 网关 | 多模型路由、熔断、限流、降级、成本追踪，模型可替换 |
| **前端** | React 18 + TypeScript + Ant Design + Zustand | 类型安全 + 组件化 + 轻量状态管理 |
| **数据库** | PostgreSQL + SQLAlchemy 2.0 | 关系型 + 成熟 ORM，async 支持 |
| **缓存/队列** | Redis + RabbitMQ + Celery | 分级缓存 + 异步任务解耦 |
| **向量库** | Milvus（降级 InMemory/Chroma） | 大规模向量检索，支持多租户分片 |
| **Embedding** | BGE-M3（降级 bge-small-zh） | 中英多语言，稠密+稀疏双向量 |
| **评测** | RAGAS + 六维评估 | 标准化指标（Faithfulness/Relevancy/Precision/Recall） |
| **可观测** | Prometheus + OpenTelemetry + structlog | 指标 + 链路追踪 + 结构化日志 |
| **部署** | Docker Compose + K8s 清单 | 一键启动 + 水平扩展 |

**选型核心原则**：
1. **模型可替换**——LLM 是商品，网关抽象掉具体厂商，不锁定某一家
2. **用工程确定性驾驭模型不确定性**——Agent 必须有 Harness 护栏
3. **评估驱动**——RAGAS/Herms 让系统"越用越好"，而非发布即巅峰

## 五、遇到的难题（及解决思路）

> 这是面试官最关心的部分。我挑 6 个最有代表性的。

### 难题 1：Agent 无限循环 / 刷爆 Token 成本

**问题**：LLM 是不确定性的，Agent 循环若不套护栏，会无限调用工具、重复推理、刷爆账单。

**解决**：设计 **Harness 层**（`src/harness/`），用代码确定性约束模型不确定性：
- 最大迭代硬上限
- Token/金额预算熔断（超预算直接 `HarnessViolation`）
- 循环检测（连续相同动作 / 交替模式）
- 高危工具拦截（CLI 每次授权）
- 独立校验器（禁止 LLM 自判——"子 Agent 欺骗主编排器是真实攻击面"）

### 难题 2：上下文压缩后，关键记忆会不会丢失

**问题**：长对话必然超出上下文窗口，简单截断会丢失用户之前说的关键信息（名字、偏好、结论）。

**解决**：**对话记忆压缩**（`src/services/conversation_memory.py`）：
- STM 滑动窗口存近期对话
- 超限时，旧对话用 LLM 摘要压缩到 LTM（而非丢弃）
- 摘要保留关键事实，作为 system message 前缀注入后续对话
- 单元测试验证："压缩后关键事实不丢失"

### 难题 3：RAG 检索不准（词面匹配 vs 语义理解）

**问题**：用 hash/keyword 检索时，"AI technology" 检索不到 "machine learning"（词不重叠但语义相关）。

**解决**：接入真实语义 embedding（BGE 系列），并做**三级自动降级**：
- bge-m3（1024d 多语言，最强）
- bge-small-zh-v1.5（512d 中文，95MB）
- hash embedder（兜底，词哈希）

验证结果：中文语义查询"AI 训练模型的技术"正确命中"机器学习"文档。

### 难题 4：Prometheus 指标重复注册（生产级 bug）

**问题**：多个 `CircuitBreaker`/`GatewayRouter` 实例各自注册同名指标，第二个实例就 `DuplicateTimeseries` 崩溃——多实例部署必崩。

**解决**：把指标改成**模块级单例**（`labelnames` 区分实例），所有实例共享同一组指标对象。这是"组件写对了但没集成测试就发现不了"的典型 bug，集成测试重写时才暴露。

### 难题 5：docker 构建卡死在重型依赖下载

**问题**：sentence-transformers 带 torch（~2GB），在慢网络下下载永远超时，docker 构建卡死。

**解决**：
- 把重型依赖（sentence-transformers/chromadb/pymilvus/dspy）从 Dockerfile 移除，改成**运行时按需安装**
- 代码做优雅降级（缺模型用 hash embedder，缺 Milvus 用 InMemory）
- docker 挂载宿主机 HF 缓存 + `HF_HUB_OFFLINE=1` 离线加载
- 本地 `.venv` 有完整依赖，跑完整 BGE 语义检索；docker 用于一键启动验证 HTTP 服务

### 难题 6：认证链 schema 不一致（隐藏 bug）

**问题**：`dependencies.py` 的认证 SQL 查询 `ak.role`（APIKey 模型没这个字段）+ `crypt()`（PostgreSQL 扩展，但模型用 SHA-256 hash），导致带认证的端点 500。

**解决**：改用 ORM + SHA-256 hash 匹配，seed demo tenant + API key，前端 axios 默认注入 `X-API-Key`。

## 六、高并发/亿级的诚实边界

**关键认知**：高并发/亿级是"运维 + 基础设施"的结果，不是纯代码写出来就成立的。

- **真实跑通（Phase 1）**：熔断/限流/降级/缓存/异步/背压/分层超时重试/无状态扩展设计
- **蓝图（Phase 2/3/4）**：分库分表/多活/GPU 集群/压测（见 `docs/亿级演进蓝图.md`）

**面试话术**："当前是 Phase 1 MVP，单机可验证的机制全部真实跑通；亿级是 Phase 4 的演进目标，我已经设计了分库分表/多活/GPU 集群/压测方案，真实验证需要真实基础设施。我诚实区分了'代码能做到的'和'需要基础设施验证的'。"

## 七、核心亮点总结（30 秒电梯陈述）

1. **十层架构 + 三大体系**：分层清晰、依赖单向、无循环依赖
2. **Harness 护栏**：用工程确定性驾驭模型不确定性
3. **Herms 自进化**：评估驱动的越用越好闭环（H-E-R-M-S）
4. **RAGAS 评测**：标准化指标量化 RAG 质量
5. **真实链路**：207 个测试全绿，0 mock 假数据
6. **诚实边界**：分得清"代码能做到"和"需要基础设施"
