# LLM 平台 · 亿级演进蓝图

> 定位：从当前 **Phase 1 MVP（单机可跑、可验证）** 演进到 **Phase 4（亿级月度请求）** 的架构方案。
> 口径：**亿级请求/月 ≈ 万级峰值 QPS**（不是亿级 QPS——后者物理上不可能，见《生产级 AI 原生应用》文档开头口径说明）。

---

## 一、诚实的能力边界（面试关键）

高并发 / 高可用 / 低延迟 / 亿级，本质是 **运维 + 基础设施** 的结果，不是纯代码"写出来就成立"的。当前代码已经做对的部分是**架构的可扩展性**；真正达到亿级需要真实的基础设施和压测，这在单机 Windows + docker 上物理上验证不了。

| 能力 | 现状（Phase 1 MVP） | 亿级目标（Phase 4） |
|---|---|---|
| 服务无状态化 | ✅ 已实现（app 无本地状态，外部 PG/Redis/消息队列） | 水平扩容的基础 |
| 熔断/限流/降级/重试 | ✅ 已实现（ai_gateway） | 分片 + 全局限流 |
| 分层超时/重试预算/断点恢复 | ✅ 已实现（resilience） | 自动调参 + 跨区域 |
| 流量染色/灰度/漂移监控 | ✅ 已实现（herms） | 多版本并行 + 自动决策 |
| 向量检索 | InMemory / Milvus（单机） | Milvus 分片集群 |
| 模型推理 | 云端 API（DeepSeek 等） | vLLM 集群 + KV Cache 分层 |
| 多可用区 / 异地多活 | ❌ 需基础设施 | 跨区域调度 + 数据同步 |

**面试话术**："当前交付的是 Phase 1 MVP——单机可验证的完整机制（熔断、限流、降级、分层超时、重试预算、断点恢复、灰度、漂移监控、RAGAS 评测）全部真实跑通；亿级的演进路径我已经设计好，分库分表、读写分离、向量分片、多 AZ、KV Cache 分层调度、异步削峰，这些在本文档有完整方案和代码骨架，但真实验证需要真实的多机房基础设施和压测。"

## 二、水平扩展设计（Phase 1 已具备的基础）

### 2.1 无状态应用 + 外部有状态存储

```
                    ┌─────────────────────────────┐
                    │   Load Balancer / API 网关   │
                    │   (APISIX / Kong / Nginx)    │
                    └──────────────┬──────────────┘
                                   │
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
        ┌──────────┐         ┌──────────┐         ┌──────────┐
        │ app #1   │         │ app #2   │         │ app #N   │
        │ (无状态)  │         │ (无状态)  │         │ (无状态)  │
        └────┬─────┘         └────┬─────┘         └────┬─────┘
             │                    │                    │
             └────────┬───────────┴──────────┬─────────┘
                      ▼                      ▼
              ┌──────────────┐        ┌──────────────┐
              │ PostgreSQL   │        │    Redis     │
              │ (读副本+N)    │        │  (Cluster)   │
              └──────────────┘        └──────────────┘
```

**关键**：`app` 层零本地状态——所有会话、缓存、限流桶都在 Redis/PostgreSQL。这意味着任意加 app 实例即可水平扩容，这是亿级的地基（已在代码中体现：`app.state` 只挂外部客户端，不存业务状态）。

### 2.2 消息队列削峰

Celery + RabbitMQ 已就位（`src/infrastructure/broker.py`），四类队列隔离：
- `realtime.chat` — 实时流式对话
- `agent.task` — Agent 任务
- `background.eval` — 后台评测 / 向量重建
- `notification` — 通知

突发流量先入队，worker 按并发消费，打不穿推理集群。

## 三、分库分表 + 读写分离（Phase 3）

### 3.1 分表策略

`RequestLog`（审计日志，写入量最大）按 `tenant_id` 哈希分表：

```python
# 代码骨架（SQLAlchemy）
# 分表键 = tenant_id 哈希 % 分片数
def shard_for(tenant_id: str, num_shards: int = 16) -> int:
    import hashlib
    return int(hashlib.md5(tenant_id.encode()).hexdigest(), 16) % num_shards

# 读写分离：写主库，读副本
# SQLAlchemy 通过 sessionmaker 绑定不同的 engine
write_engine = create_async_engine(WRITE_URL)      # 主库
read_engine  = create_async_engine(READ_URL)       # 读副本
```

### 3.2 读写分离

- **写**：走主库（`async_sessionmaker(bind=write_engine)`）
- **读**：走读副本（`async_sessionmaker(bind=read_engine)`），报表查询、文档列表等只读端点
- **一致性**：最终一致，读副本延迟 < 1s（主从复制）

## 四、向量库分片（Phase 3）

### 4.1 Milvus 分片集群

```
┌─────────────────────────────────────────────┐
│                 Milvus Cluster              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐    │
│  │ Shard 0  │ │ Shard 1  │ │ Shard N  │    │
│  │ tenant 0 │ │ tenant 1 │ │ tenant N │    │
│  └──────────┘ └──────────┘ └──────────┘    │
└─────────────────────────────────────────────┘
```

- **分片键**：`tenant_id`（多租户隔离）+ `collection`（按知识库分表）
- **召回率权衡**：分片检索 vs 全量检索——亿级向量时，分片后单分片延迟可控，但需实测召回率损失（文档风险清单第 2 条）
- **BGE-M3 双向量**：dense（1024d）+ sparse 混合检索，支持跨分片 RRF 融合

## 五、模型层扩展（Phase 3/4）

### 5.1 vLLM 推理集群（需 Linux + GPU，Windows 物理无法运行）

```
┌───────────────────────────────────────────────┐
│              vLLM Cluster (GPU)               │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐         │
│  │ GPU 0   │ │ GPU 1   │ │ GPU N   │         │
│  │ LoRA A  │ │ LoRA B  │ │ LoRA C  │ 热加载  │
│  └─────────┘ └─────────┘ └─────────┘         │
└───────────────────────────────────────────────┘
```

- **多模型路由**：代码 → DeepSeek-Coder，复杂规划 → Claude，分类/摘要 → 小模型（成本优化）
- **LoRA 热加载**：不停机切换微调 adapter
- **KV Cache 四层**：GPU → CPU → SSD → 远端（PagedAttention）

### 5.2 Agent 感知路由

结合活跃会话数、会话热度、KV 占用动态调度（文档 2.7 节）：
- 热门会话 → 常驻 KV，避免重复 prefill
- 冷会话 → KV 降级到 SSD/远端
- 突发流量 → 预抢占 + 削峰缓冲

### 5.3 四类队列隔离

| 队列 | 优先级 | 说明 |
|---|---|---|
| realtime.chat | 最高 | 流式对话，低延迟 |
| agent.task | 高 | Agent 多步任务 |
| background.eval | 低 | 评测/向量重建 |
| background.batch | 最低 | 离线批处理 |

## 六、异地多活 + 跨区域调度（Phase 4）

### 6.1 架构

```
        ┌────────── 全球流量入口（DNS / Anycast）──────────┐
        │                                                 │
   ┌────▼────┐          ┌────▼────┐          ┌────▼────┐
   │ Region A│          │ Region B│          │ Region C│
```

## 七、压测方案 + 容量规划

### 7.1 压测工具

- **locust**（HTTP 层）/ **k6**（WebSocket/SSE 流式）
- **代码骨架**：

```python
# locustfile.py（骨架）
from locust import HttpUser, task, between

class ChatUser(HttpUser):
    wait_time = between(0.1, 0.5)

    @task
    def chat(self):
        self.client.post("/v1/gateway/chat/completions", json={
            "model": "deepseek-chat",
            "messages": [{"role": "user", "content": "hello"}],
        })
```

### 7.2 容量指标（Phase 4 目标）

| 指标 | 目标 |
|---|---|
| 峰值 QPS | 万级（≈ 亿级请求/月） |
| P99 延迟 | < 2s（流式首 token < 500ms） |
| 可用性 | 99.9%（月度） |
| 错误率 | < 0.5% |

### 7.3 成本归因

全维度计量（不只 LLM Token）：
- `input_tokens` / `output_tokens`
- `tool_duration_ms`（工具耗时）
- `gpu_seconds`（GPU 占用）
- `vector_search_count`（向量检索次数）
- `sandbox_cpu_seconds`（沙箱 CPU）

## 十、总结

**演进路径清晰**：
- **V1（当前）**：能跑——单机可验证的完整机制全部真实跑通
- **V2**：能运营——可观测、可排障、可计费、可合规
- **V3**：能扛突发——分库分表、向量分片、多 AZ、压测
- **V4**：亿级——异地多活、跨区域调度、KV Cache 深度优化

核心资产是**架构纪律**（分层、无状态、韧性、灰度、评测闭环），不是某一行代码。这正是面试要讲的"系统思考"。
